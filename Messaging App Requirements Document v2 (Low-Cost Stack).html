Text Messaging Application — Requirements Document

📄 Version: 2.0 📅 Date: September 2026 🏗️ Stack: .NET MAUI Blazor Hybrid (Android) · ASP.NET Core Web API + SignalR · PostgreSQL (Supabase)

1. Executive Summary

This document defines the functional, technical, and architectural requirements for a cross-platform text messaging application. It is a cost-driven and scope-driven rewrite of an earlier Azure-based, WhatsApp-style design: the original design (Cosmos DB, Azure Communication Services calling, Notification Hub, API Management, Redis, Key Vault) was estimated to run $150–500+/month even at low traffic. This version targets $0–10/month by swapping every paid Azure service for a free-tier or self-hosted equivalent, and by narrowing v1 scope to its essential core: reliable, real-time text messaging. Media sharing and voice/video calling are both explicitly deferred to later phases (see §13) rather than cut permanently — the architecture is designed so they can be added without a rewrite.

Frontend.NET MAUI Blazor Hybrid — Android primary, iOS optional/later
BackendASP.NET Core Web API + SignalR Hub, self-hosted in Docker
DatabasePostgreSQL via Supabase (free tier)
PushFirebase Cloud Messaging (FCM) — direct, free
HostingSmall VPS (Oracle Free Tier / Hetzner) + Nginx + Cloudflare
DeferredMedia sharing & voice/video calling — Phase 2/3

2.1 Core Feature Set (v1)

Messaging

  • Group text chats
  • Emoji reactions
  • Message edit & delete
  • Sent / Delivered / Read receipts
  • Typing indicators
User Management

  • JWT authentication

  • Online / Offline presence

Notifications
  • Push notifications (FCM, Android)
  • In-app message alerts
  • Background delivery
Not in v1

  • Voice & video calling

⏳ Deferred to Phase 2 / Phase 3

Media sharing (photos, videos, documents, voice messages) and voice/video calling are intentionally out of v1 scope. Both add real infrastructure cost and complexity (object storage, antivirus scanning, TURN relays, per-minute billed calling SDKs) that isn't justified until the core text messaging experience is solid and in real users' hands. See §13 for the phased roadmap and what each addition will cost.

Splash Screen

Purpose

Display the application logo and branding while the app performs startup initialization (loading configuration, checking auth token, preloading services). Automatically navigates away after 2–3 seconds.

Layout
  • Full-screen solid background (brand color)
  • Centered app logo (SVG / PNG, 120×120 dp)
  • App name in white bold text below logo
  • Version number at bottom center
  • Activity indicator while initializing
Components / Controls
  • ContentPage — full screen, no shell chrome
  • Image — app logo
  • Label — app name, version
  • ActivityIndicator — loading state
User Actions
  • None — passive screen, no tappable elements
  • Cannot navigate back (no back stack entry)
Navigation Flow
  • If valid JWT token found → navigate to Home (Chats)
  • If no token / token expired → navigate to Login Screen
  • Minimum display: 2 s; maximum: 3 s regardless of init speed
Startup Logic (ViewModel)
  • Check SecureStorage for stored JWT access token
  • Validate token expiry locally (decode JWT claims)
  • If token close to expiry (<5 min) — silently call refresh endpoint
  • Initialize SignalR connection if token valid
  • Register device for push notifications

4. MAUI Application Architecture

The app follows strict MVVM using .NET MAUI Blazor Hybrid. Blazor Razor components handle the UI; C# ViewModels handle state and commands; Services handle all external communication. Framework choice is unchanged from the original design — MAUI itself has no cloud dependency, so nothing here changed for cost reasons. What changed is scope: calling and media services are removed from v1.

4.1 MVVM Structure

LayerTechnologyResponsibility
ViewBlazor Razor Components (.razor)UI rendering, data binding via @bind, event handling
ViewModelC# classes inheriting ObservableObject (CommunityToolkit.Mvvm)State management, commands, validation logic
ServiceC# interfaces + implementationsAPI calls, SignalR hub, local storage, device APIs
ModelPlain C# record / classDTOs, domain entities, API response models

This is simpler than the original design: dropping Cosmos DB means there's no change-feed processor to run — the API pushes to SignalR directly, in the same request, right after the database write succeeds.

6. PostgreSQL Database Design

Database: text_messaging_db — standard PostgreSQL, hosted on Supabase's free tier (500MB, generous for a text-only app; a self-hosted Postgres instance on the same VPS is a documented drop-in alternative if you'd rather avoid Supabase entirely). Relational tables replace Cosmos DB's document containers; JSONB is used only where the shape is genuinely flexible (reactions).

6.1 Tables Summary

TableKeyPurpose
usersid (PK)User profiles, auth credentials, settings
conversationsid (PK)Chat metadata: type, name (for groups), last message pointer
conversation_participants(conversation_id, user_id) composite PKJunction table — who is in which conversation. Replaces the original's embedded participants array; a real improvement Postgres makes easy.
messagesid (PK), indexed on (conversation_id, sent_at)All text messages. No attachments column in v1 — intentionally simplified since media isn't in scope.
user_settingsuser_id (PK, FK)Per-user preferences, notification settings
device_tokensid (PK), FK user_idFCM registration tokens per device
refresh_tokensid (PK), FK user_idJWT refresh tokens with expiry

The calls table from the original design is Phase 2 and omitted from the v1 schema entirely — it will be added alongside calling, not before.

6.2 Core Table Definitions

CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    display_name    VARCHAR(100) NOT NULL,
    phone_number    VARCHAR(20) UNIQUE NOT NULL,
    email           VARCHAR(255) UNIQUE,
    password_hash   TEXT NOT NULL,
    status_message  VARCHAR(140) DEFAULT 'Available',
    avatar_url      TEXT,              -- optional, small profile picture only
    is_online       BOOLEAN NOT NULL DEFAULT false,
    last_seen_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE conversations (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_type VARCHAR(10) NOT NULL CHECK (conversation_type IN ('direct','group')),
    group_name        VARCHAR(100),               -- null for direct conversations
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE conversation_participants (
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role            VARCHAR(10) NOT NULL DEFAULT 'member',
    unread_count    INT NOT NULL DEFAULT 0,
    is_muted        BOOLEAN NOT NULL DEFAULT false,
    is_pinned       BOOLEAN NOT NULL DEFAULT false,
    joined_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (conversation_id, user_id)
);

CREATE TABLE messages (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id   UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    sender_id         UUID NOT NULL REFERENCES users(id),
    text              VARCHAR(4096) NOT NULL,
    reply_to_message_id UUID REFERENCES messages(id),
    reactions         JSONB NOT NULL DEFAULT '[]',   -- [{ "userId": "...", "emoji": "❤️" }]
    status            JSONB NOT NULL DEFAULT '{}',   -- { "userId": "sent"|"delivered"|"read" }
    is_edited         BOOLEAN NOT NULL DEFAULT false,
    edited_at         TIMESTAMPTZ,
    is_deleted        BOOLEAN NOT NULL DEFAULT false,
    deleted_at        TIMESTAMPTZ,
    sent_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_messages_conversation_sent ON messages (conversation_id, sent_at DESC);

Example row — messages

id: 99z7w1v3-...

6.3 Indexing Strategy

  • messages(conversation_id, sent_at DESC) — supports cursor-based pagination of a conversation's history, the app's hottest query
  • users(phone_number) unique index — login lookup and duplicate-registration checks
  • conversation_participants(user_id) — supports "get my conversations" queries efficiently

7. Media Storage — Deferred (Phase 2/3)

This section is intentionally a stub — the full design gets written when this phase is actually scheduled, not before, so it reflects real v1 learnings rather than upfront guesswork.

10.2 Phase 2 — Calling Technology Direction

🔭 Not built for v1 — direction only

Hosted calling SDKs (Azure Communication Services, Twilio, Agora) all bill per-minute and were the single biggest cost driver in the original design. When calling is added, the recommended direction is self-hosted WebRTC: browser/MAUI WebRTC peer connections negotiated over the existing SignalR hub, using a free public STUN server (e.g. Google's) for NAT discovery, with a self-hosted coturn TURN relay on a small VPS (~$5/mo added) as a fallback for the ~10-20% of connections that can't establish a direct P2P path. This keeps calling essentially free at low volume instead of metered per minute.

10.4 Presence Design (In-Memory)

  • A singleton PresenceTracker service holds a ConcurrentDictionary<string, DateTime> mapping userId → last-seen-active timestamp
  • On SignalR connect: dictionary entry set/refreshed; broadcast UserPresenceChanged(online)
  • Heartbeat every 60s refreshes the timestamp; a background timer sweeps entries older than 5 minutes and marks them offline
  • On disconnect: entry removed immediately + broadcast UserPresenceChanged(offline)
  • GET /users/{userId}/presence reads the in-memory tracker (falls back to the users.last_seen_at column if absent)

Single-server assumption: this works because v1 runs one backend instance. If/when traffic requires scaling to multiple instances, presence (and the SignalR backplane) needs to move to Redis — that's a Phase 2/3 infrastructure upgrade, not a v1 concern.

11. Security Requirements

11.1 Authentication & Authorization

RequirementImplementation

Account LockoutLock for 15 minutes after 5 consecutive failed logins (tracked in-memory alongside presence, per §10.4)
AuthorizationEvery message/conversation API validates that the requesting userId is a participant in the conversation

11.2 Data Encryption & Secrets

  • In Transit: TLS 1.2+ enforced on all endpoints via Nginx + Let's Encrypt; HSTS headers
  • At Rest: Supabase's underlying PostgreSQL storage is encrypted at rest by the provider by default
  • Secrets: connection strings, JWT signing key, and FCM service-account credentials live in a gitignored .env file and/or Docker secrets — no dedicated secrets-manager service for v1; revisit only if a future compliance requirement demands one
  • Device Storage: JWT tokens stored in platform SecureStorage (Android Keystore)

11.3 File Upload Security

Deferred to Phase 2/3 alongside media support (see §7) — MIME/magic-byte validation and optional self-hosted ClamAV scanning will be designed when file upload is actually built. There is no file upload surface in v1 to secure.

11.4 API Security

  • Rate limiting: 100 requests/min per user, enforced via ASP.NET Core's built-in rate-limiting middleware (or Nginx limit_req as a second layer)
  • CORS restricted to known MAUI app origins
  • Input validation with FluentValidation on all request bodies
  • SQL injection prevented via parameterized queries / EF Core throughout
  • All error responses return generic messages (no stack traces in production)
