Native SMS Messenger — Requirements Document

📄 Version: 1.0 📅 Date: September 2026 🏗️ Stack: .NET MAUI (Android) · Native Android Telephony APIs · No Backend

1. Executive Summary

This document defines the requirements for a native Android SMS/MMS messenger app. Unlike an over-the-top (OTT) chat app such as WhatsApp — where both people must have the same app installed and messages travel through a company's own servers — this app sends and receives real SMS text messages through the phone's own cellular connection, using Android's native telephony APIs. That means it can reach any phone number, on any carrier, on any device, because the message itself is an ordinary text message, not a proprietary chat protocol.

This project has gone through three scope changes before landing here, each one trading features for lower cost and broader reach: it started as a full WhatsApp-style clone on Azure (Cosmos DB, Azure Communication Services calling, Notification Hub — realistically $150–500+/month at low volume); that was rebuilt around a low-cost self-hosted/Supabase stack focused on text-only messaging; and finally it became clear that what was actually wanted was real SMS interoperability, which changes the architecture entirely. Because SMS delivery rides the user's own cellular connection instead of a server we operate, this version needs no backend, no cloud database, and no monthly infrastructure bill at all for v1.

PlatformAndroid only (API 24+) — not a priority choice, a platform capability limit; see below
Client.NET MAUI Blazor Hybrid, with Android-native platform code for telephony access

⚠️ Why Android only, not "Android first"

Apple does not allow third-party iOS apps to send or receive SMS/MMS through the carrier network the way Android does — there is no equivalent of Android's default-SMS-app role on iOS. This isn't a prioritization decision that a later phase revisits; it's a platform restriction. If cross-platform reach is ever wanted, it would require a completely different mechanism (a cloud SMS gateway with a rented phone number — see the Phase 2/3 Roadmap), which reintroduces a paid backend and stops being "the user's own phone number."

2. What Real SMS Can & Can't Do

This is the most important section in this document. Plain SMS is a carrier protocol, not a chat protocol — it does not support several features that a WhatsApp-style app takes for granted. Nobody building or using this app should be surprised these are missing.

🚫 Not achievable over SMS, in any phase

  • Typing indicators — there is no such signal in the SMS protocol. Not planned for any future phase; it cannot exist here.
  • Cross-network read receipts — the carrier network confirms only that a message was delivered to the recipient's device (a delivery report), never that a person opened and read it. This app can mark a thread "read" locally when you open it, but that status is never transmitted to the sender — it is not the same thing as WhatsApp's blue double-tick, and this document never uses that framing.
  • Emoji reactions, edit-after-send, delete-for-everyone — SMS is a one-way, fire-and-forget message. Once sent, there is no protocol mechanism for the recipient's device to be told "react to that," "replace that text," or "forget that." These are not deferred to a later phase — they are simply not possible over plain SMS, ever, on any carrier.
  • True shared group threads — a WhatsApp-style group (one shared conversation, visible replies from everyone) generally needs MMS group-messaging support on the carrier side, which this app does not implement in v1. See the "individual group texting" note below for what v1 actually does instead.

✅ What v1 actually achieves

  • Sent → Delivered status — SmsManager accepts a sentIntent (fires when the message leaves the device) and a deliveryIntent (fires when the carrier confirms delivery). This gives a genuine two-state status per message, the SMS equivalent of a single tick (sent) and a double tick (delivered) — with no third "read" tick, because that signal doesn't exist on this protocol.
  • "Individual group texting" — sending the same text to multiple recipients at once. Each recipient receives it as an ordinary 1:1 text from you; they do not see each other, do not see each other's replies, and there is no shared thread. This is clearly labeled as such in the app UI so it's never confused with a real group chat. Proper MMS group threads are a Phase 2 item (see the Roadmap).
  • Reach — any phone number, any carrier, any device, with zero per-message cost beyond the user's existing cellular plan.

4. Android SMS Integration Architecture

This section replaces everything a cloud-backend architecture would normally cover. There is no server here — this is entirely about how the app talks to Android's own telephony subsystem.

4.1 The Default-SMS-App Contract

Android routes incoming SMS differently depending on whether an app is the user's designated default SMS app. A non-default app only receives the read-only SMS_RECEIVED_ACTION broadcast (informational, can't reliably own message state). The OS-designated default SMS app additionally receives the protected SMS_DELIVER_ACTION broadcast, and is expected to be the one writing incoming messages into the shared SMS content provider. To manage conversations reliably — and to be allowed to request the sensitive READ_SMS/RECEIVE_SMS permissions from Google Play at all — this app must become the user's default SMS app.

4.2 Components Required to Be Eligible

ComponentAndroid RequirementPurpose
BroadcastReceiverHandles SMS_DELIVER_ACTION (and stubs WAP_PUSH_DELIVER_ACTION for future MMS)Receives incoming SMS content directly from the OS
Compose ActivityHandles ACTION_SENDTO (sms:/smsto:) and ACTION_SEND (text/plain)Lets other apps hand off "text this number" intents to this app
HeadlessSmsSendServiceHandles ACTION_RESPOND_VIA_MESSAGEEnables quick-reply from notifications/other apps without opening the UI

4.3 Requesting the Default Role

// Android 10+ (API 29+) — primary path
var roleManager = (RoleManager)GetSystemService(RoleService);
var intent = roleManager.CreateRequestRoleIntent(RoleManager.RoleSms);
StartActivityForResult(intent, RequestDefaultSmsAppCode);

// Pre-API 29 devices fall back to:
// Telephony.Sms.Intents.ActionChangeDefault

4.4 Sending Messages

// Short message
smsManager.SendTextMessage(destinationAddress, null, messageBody, sentIntent, deliveryIntent);

// Long message — split across parts, single logical message in the UI
var parts = smsManager.DivideMessage(messageBody);
smsManager.SendMultipartTextMessage(destinationAddress, null, parts,
    sentIntents, deliveryIntents);

// sentIntent fires  → message left the device       (Sent)
// deliveryIntent fires → carrier confirmed delivery  (Delivered)
// no further signal exists for "read"

4.5 Reading Data — the OS Owns Storage, Not This App

  • Telephony.Sms.CONTENT_URI — individual SMS rows (address, body, date, read flag, type)
  • Telephony.Threads.CONTENT_URI / the MMS-SMS conversations provider — groups messages into threads by participant set
  • No app-owned message database is created — the app is a viewer/composer over data Android already persists and manages

4.6 Contacts Resolution

Phone numbers are resolved to display names and photos by querying ContactsContract (ContactsContract.PhoneLookup), used to render the Conversations list and Thread Detail header. Numbers with no matching contact are shown as formatted raw numbers.

4.7 Required Permissions

PermissionWhy it's needed
READ_SMSRead existing message history from the content provider
SEND_SMSSend outgoing messages via SmsManager
RECEIVE_SMSReceive the SMS_DELIVER_ACTION broadcast as the default SMS app
RECEIVE_MMSRequired to remain a valid default-SMS-app candidate, even though MMS composing isn't built in v1
READ_CONTACTSResolve numbers to names/photos
READ_PHONE_STATERead device phone number / dual-SIM subscription info
POST_NOTIFICATIONSAndroid 13+ runtime permission for local incoming-message notifications

Every permission is requested at runtime with a plain-language explanation shown immediately before the system prompt, per Android's permission best practices — and because READ_SMS/RECEIVE_SMS sit in Google Play's restricted-permissions category, being a genuinely functioning default SMS app is one of the few declared use cases Google accepts for them.

4.8 Dual-SIM Handling (optional nicety)

SubscriptionManager and SmsManager.GetSmsManagerForSubscriptionId allow the user to choose which SIM sends a given message on dual-SIM devices. Not required for v1 to function, but low-effort to add given the send path already goes through SmsManager.

6. Data Model

There is no app-owned database, local or remote, for v1. Android's own SMS/MMS content provider (backed by the OS's own SQLite storage) is the single source of truth for every message and thread — the app reads and writes through it rather than duplicating it.

ℹ️ The only local storage this app has

A handful of small app preferences via MAUI Preferences — whether onboarding is complete, notification toggle state, and a preferred-SIM choice on dual-SIM devices. Not a database; just a few key-value settings.

7. Notifications

When SmsDeliverReceiver fires (a new message arrived) and the app is not in the foreground, the app raises a local notification directly via Android's NotificationManager. There is no cloud round-trip of any kind — Android already delivered the message straight to the device before the app ever gets involved, so there is nothing for Firebase or any other push service to do here.

8. Permissions & Privacy

See section 4.7 for the full permission list and justification for each. Because there is no cloud backend in v1, there is no server-side encryption-in-transit or encryption-at-rest concern to design for — all message content stays on-device, inside Android's own storage, under the same protection the OS already provides to its default messaging app.

  • No message content ever leaves the device except as an actual SMS sent over the carrier network (which is inherent to how SMS itself works, not something this app adds)
  • No account, login, or identity system exists in v1 — the "identity" is simply the device's own SIM/phone number
  • Every sensitive permission request includes an in-app rationale shown before the OS prompt

9. Cost Summary

💰 v1 Infrastructure Cost: $0/month

No servers, no cloud database, no push notification service, no third-party messaging API. The only "cost" of sending a message is whatever the user's own cellular plan already charges for SMS — typically unlimited on modern plans. Google Play Developer registration ($25 one-time) is the only fixed cost associated with shipping this app at all.
