Mobile Chat Application — Requirements Document

📄 Version: 1.0 📅 Date: June 2026 🏗️ Stack: .NET MAUI Blazor Hybrid · .NET Web API · Azure Cosmos DB

1. Executive Summary

This document defines the complete functional, technical, and architectural requirements for a cross-platform mobile chat application — a WhatsApp-style clone built on the Microsoft Azure ecosystem. It serves as the single source of truth for developers, testers, architects, and project managers throughout the entire development lifecycle.

Frontend.NET MAUI Blazor Hybrid (iOS, Android, Windows, macOS)
BackendASP.NET Core Web API + SignalR Hub
DatabaseAzure Cosmos DB (NoSQL, globally distributed)
MediaAzure Blob Storage + Azure CDN
CallingAzure Communication Services (Voice + Video)
PushAzure Notification Hub (FCM + APNS)

Splash Screen

Purpose

Display the application logo and branding while the app performs startup initialization (loading configuration, checking auth token, preloading services). Automatically navigates away after 2–3 seconds.

Layout
  • Full-screen solid background (brand green #25D366)
  • Centered app logo (SVG / PNG, 120×120 dp)
  • App name in white bold text below logo
  • Tagline text (optional, smaller weight)
  • Version number at bottom center
  • Activity indicator while initializing
Components / Controls
  • ContentPage — full screen, no shell chrome
  • Image — app logo
  • Label — app name, tagline, version
  • ActivityIndicator — loading state
  • CSS animation — fade-in on logo
User Actions
  • None — passive screen, no tappable elements
  • Cannot navigate back (no back stack entry)
Navigation Flow
  • If valid JWT token found → navigate to Home (Chats)
  • If no token / token expired → navigate to Login Screen
  • Minimum display: 2 s; maximum: 3 s regardless of init speed
Startup Logic (ViewModel)
  • Check SecureStorage for stored JWT access token
  • Validate token expiry locally (decode JWT claims)
  • If token close to expiry (<5 min) — silently call refresh endpoint
  • Initialize SignalR connection if token valid
  • Register device for push notifications

Chats Screen

Purpose

The central hub of the application. Displays a chronologically sorted list of all conversations the authenticated user is part of, with last-message previews and unread counts.

Layout Description

  • Top Navigation Bar (fixed) — App logo left, search icon right, optional overflow menu (New Chat)
  • Search Bar — Collapsed by default; expands inline when search icon tapped
  • Conversation List — Scrollable ListView / CollectionView, each row is a ConversationCell
  • FAB (Floating Action Button) — bottom-right, opens New Chat / New Group dialog
  • Footer Tab Bar (fixed) — Chats · Calls · Profile tabs
Conversation Cell Layout
  • Avatar (circular image, 48 dp) — left
  • Contact name — bold, 14sp
  • Last message preview — grey, 12sp, max 1 line, truncated
  • Timestamp — top right, 11sp
  • Unread badge — green pill, top-right over avatar
  • Message status icon (✓✓ read receipt) for own messages
  • Online indicator — green dot on avatar
  • Muted icon — if conversation is muted
Components / Controls
  • CollectionView — conversation list with virtualization
  • SearchBar — live filter
  • RefreshView — pull-to-refresh
  • SwipeView — swipe left: Archive / Delete; swipe right: Mark Read
  • Shell.TabBar — bottom navigation
  • ImageButton — FAB for new conversation
  • ActivityIndicator — initial load state
User Actions
  • Tap conversation → open Chat Details
  • Long-press → context menu (Archive, Mute, Delete, Pin)
  • Swipe left → Delete / Archive
  • Swipe right → Mark as Read
  • Tap search → expand search bar
  • Type in search → filter conversations & contacts
  • Pull down → refresh conversation list
  • Tap FAB → New Chat screen
Navigation Flow
  • Tap conversation → Chat Details Screen
  • Tap Calls tab → Calls Screen
  • Tap Profile tab → Profile Screen
  • Tap FAB → New Chat / Contact Picker
  • Search result tap → Chat Details Screen (or create new)

Search Behaviour

  • Local filter applied immediately on keypress (no debounce needed for local data)
  • Remote contact search triggered after 300 ms debounce when no local match
  • Search covers: contact name, phone number, last message content
  • Results grouped: Conversations | Contacts

Validation Rules

  • Empty state shown when no conversations exist: illustration + "No conversations yet. Start chatting!"
  • No-results state shown when search returns nothing
  • Network error banner shown at top if API call fails (non-blocking)

Chat Detail Screen

Purpose

Displays the complete message history between participants and provides all messaging capabilities including text, media, files, emoji reactions, and real-time status indicators.

Layout Description

  • Top App Bar (fixed) — Back arrow · Contact avatar · Contact name + online status · Video call icon · Voice call icon · Overflow menu
  • Message List — Scrollable CollectionView, newest at bottom, grouped by date
  • Typing Indicator Row — appears above input bar when remote user is typing
  • Input Bar (fixed bottom) — Emoji button · Text field (expandable, max 5 lines) · Attachment button · Send / Mic button (toggle)
Message Bubble Layout
  • Own messages — right-aligned, green bubble
  • Others' messages — left-aligned, white bubble
  • Timestamp inside bubble, bottom-right, 10sp
  • Status icons: ⏱ Sending · ✓ Sent · ✓✓ Delivered · ✓✓ (blue) Read
  • Avatar shown left for group chats only
  • Sender name shown in group chats (above bubble)
  • Edited label for edited messages
  • Reply-to quote block if message is a reply
  • Emoji reaction pills below bubble
Message Types
  • Text — plain text, auto-link URLs
  • Image — thumbnail preview, tap to expand
  • Video — thumbnail + play button
  • Document — file icon + name + size
  • Audio — waveform + play/pause + duration
  • Voice message — recorded in-app
  • System messages — "User joined", "Call ended" etc.
User Actions
  • Type text + tap Send → send message
  • Hold mic → record voice message
  • Tap 📎 → file/image/camera picker
  • Long-press bubble → context menu (Reply, Copy, Forward, React, Edit, Delete)
  • Double-tap bubble → quick ❤️ reaction
  • Tap reaction pill → see who reacted
  • Tap image → full-screen viewer
  • Swipe right on message → reply
  • Tap contact name → Contact Info screen
  • Tap call icons → initiate call
Real-Time Features
  • Messages appear instantly via SignalR
  • Typing indicator: "John is typing…" appears within 1 s of remote keypress
  • Typing indicator disappears after 3 s of inactivity
  • Read receipts update when recipient opens conversation
  • Online/offline status updates in app bar
  • Message delivery status ticks update in real time

Attachment Flow

  • Tap 📎 → bottom sheet with options: Gallery, Camera, Document, Location
  • Selected file → upload to Azure Blob Storage via POST /api/files/upload
  • Upload progress bar shown in message bubble placeholder
  • On upload success → Blob URL stored; message sent with URL reference
  • Max file size: Images 16 MB, Documents 100 MB, Video 64 MB

Validation Rules

  • Send button disabled when text field empty and no attachment selected
  • File type whitelist enforced: images (jpg, png, gif, webp), documents (pdf, docx, xlsx, pptx, txt, zip), audio (mp3, ogg, aac), video (mp4, mov)
  • File size validation client-side before upload attempt
  • Network offline banner shown; queued messages sent on reconnect
  • Message edit allowed only within 15 minutes of sending
  • Message delete: "Delete for me" always; "Delete for everyone" within 60 minutes

4. MAUI Application Architecture

The app follows strict MVVM pattern using .NET MAUI Blazor Hybrid. Blazor Razor components handle the UI; C# ViewModels handle state and commands; Services handle all external communication.

4.1 MVVM Structure

LayerTechnologyResponsibility
ViewBlazor Razor Components (.razor)UI rendering, data binding via @bind, event handling
ViewModelC# classes inheriting ObservableObject (CommunityToolkit.Mvvm)State management, commands, validation logic
ServiceC# interfaces + implementationsAPI calls, SignalR hub, local storage, device APIs
ModelPlain C# record / classDTOs, domain entities, API response models

Database: ChatAppDB — using Azure Cosmos DB NoSQL API with automatic indexing and global distribution.

7.3 SAS Token Strategy

  • All read requests for private blobs are served via short-lived SAS URIs (default 1-hour TTL)
  • Client calls GET /api/files/{fileId}/url to receive a fresh SAS URI; result cached client-side for 55 minutes
  • Upload SAS tokens (write-only, 15-min TTL) issued by API after file metadata validation
  • Public blobs (avatars, thumbnails) served via Azure CDN for global performance

10.4 Presence Design (Redis)

  • On SignalR connect: SETEX presence:{userId} 300 "online" (5-min TTL)
  • Heartbeat every 60 s resets TTL: ensures stale connections don't show as online
  • On disconnect: DEL presence:{userId} + broadcast UserPresenceChanged event
  • API endpoint GET /users/{userId}/presence reads Redis key (falls back to Cosmos lastSeenAt if key absent)

11. Security Requirements

11.1 Authentication & Authorization

RequirementImplementation
JWT Access TokenHS256 signed, 15-minute expiry, claims: userId, email, roles
Refresh TokenOpaque random string (256-bit), 30-day expiry, stored hashed in Cosmos DB refreshTokens container
Token RotationEach refresh call issues a new refresh token and invalidates the old one (rotation + reuse detection)
Password Storagebcrypt with cost factor 12 (never store plaintext)
Account LockoutLock for 15 minutes after 5 consecutive failed logins (tracked in Redis)
AuthorizationEvery message/conversation API validates that requesting userId is a participant in the conversation

11.2 Data Encryption

  • In Transit: TLS 1.2+ enforced on all endpoints; HSTS headers; certificate pinning in MAUI app
  • At Rest: Azure Cosmos DB and Azure Blob Storage use AES-256 encryption at rest by default
  • Secrets: All connection strings and API keys stored in Azure Key Vault; accessed via Managed Identity
  • Device Storage: JWT tokens stored in platform SecureStorage (iOS Keychain / Android Keystore)

11.3 Secure File Uploads

  • Server-side MIME type validation (magic bytes inspection, not just extension)
  • Antivirus scan via Azure Defender for Storage (event-driven scan on blob write)
  • Max file size enforced at API middleware before reading stream
  • Files stored with GUID names (no original filename in path) to prevent path traversal
  • Read access requires authenticated SAS token; direct public access disabled on media containers

11.4 API Security

  • Rate limiting: 100 requests/min per user via Azure API Management policy
  • CORS restricted to known MAUI app origins
  • Input validation with FluentValidation on all request bodies
  • SQL injection not applicable (NoSQL); Cosmos DB query parameterization used throughout
  • All error responses return generic messages (no stack traces in production)
